# 3B P0 缺陷根因速报（D-3B-02 / D-3B-03 / D-3B-04）

> 只读分析，不改代码。一切结论以 Motrix 原版源码 + 3B 适配层 `android/app/src/main/assets/mobile-adapt.{css,js}` + `renderer-overrides/*` 既有提案为证据，逐条标 `file:line`。
> 复现基线：K60，`innerWidth=880`，3B `#/downloads`；顶栏 `.window-chrome=0,0 880×40`；Motrix logo 按钮 `@12,7 72×40`；切换边栏 `@94,7 40×40`；新建任务 `@140,7 40×40`；「全部下载」筛选（`StatusTitleMenu`）侧栏展开 `@200,8 40×40`；JS 派发 pointer 隐藏侧栏后 `@8,8 40×40`（与 logo 12–84 横向重叠）。

## 0. 结论先行

| 缺陷 | 一句话根因 | 性质 |
|---|---|---|
| **D-3B-03**（下载状态分类栏与 M·O 重叠） | 3B 顶栏避让补丁全部锁在 `@media (max-width: 767.98px)`；K60 视口 **880 > 767.98** 落在「未覆盖带」。侧栏一收起，`SidebarInset` 靠 `ms-2` 把内容左边界压到 **x=8**（展开态是 200），而顶栏被 3B 改成**全宽不透明实底**（40px），标题进入 0–40px 带后与 logo「M·O」(12–84) 重叠。 | 断点未覆盖 + 实底顶栏叠加 |
| **D-3B-04**（侧栏隐藏后难召回） | 召回按钮 `[data-slot="sidebar-trigger"]` 原始 `size-7 = 28px`，**低于 44dp 触控热区**；且折叠后它正处在内容 x≈8 起的重叠区。层级本身未被拦截（该按钮在顶栏 `z-[60]`，内容标题仅 `z-40`，按钮在上），问题是**热区太小 + 视觉被 M·O/内容叠压**。 | 触控热区不足 |

## 2. D-3B-03：下载「状态分类栏 / 全部下载」与 M·O 重叠

### 2.1 真实 DOM 与选择器
- 该「全部下载」+下拉，是**下载页 PanelShell 的标题槽** `StatusTitleMenu`：
  - 容器页：`src/renderer/routes/downloads/downloads-page.tsx:408-435` —— `<PanelShell title={<StatusTitleMenu/>} … headerClassName="compact-header:py-1" contentClassName="px-6" footer={<GlobalStatsBar/>}>`，页面根 `div.relative.flex.h-full.min-h-0.flex-col.overflow-hidden`（:402-406）。
  - 触发按钮：`src/renderer/routes/downloads/status-title-menu.tsx:36-42` ——
    `button.app-no-drag.relative.z-[40].flex.h-9.min-w-0.items-center.gap-1.compact-header:h-7`，内含 `<h1 class="select-none text-2xl font-semibold tracking-tight compact-header:text-sm compact-header:leading-[28px]">` + chevron。
  - 它确实位于 **`[data-slot="panel-shell-header"]` 之内**（不是脱离 PanelShell 的自绘头）→ 命中官方两轴避让的正常路径。

### 2.2 侧栏隐藏后 x 从 200 → 8 的机制（源码精确吻合）
- 侧栏 `AppSidebar` 用 `variant="inset" collapsible="offcanvas"`（`app-sidebar.tsx:63-67` + `sidebar.tsx:176`）。
- 展开：`SidebarInset` 走 `md:peer-data-[variant=inset]:ms-0`（`sidebar.tsx:341`），前有 200px `sidebar-gap` → 内容左边界 = **200**。
- 收起：offcanvas → `sidebar-gap` `w-0`（`sidebar.tsx:244`）、`sidebar-container` 左移 −200（`:256`）；`SidebarInset` 走 `md:peer-data-[variant=inset]:peer-data-[state=collapsed]:ms-2`（`sidebar.tsx:341`）→ 左边界 = **8**。
- ⇒ 实测 `200 → 8` 的 192px 位移 = 侧栏宽度被抽走，**内容卡左边界精确落到 x=8**（不是缺某段 padding，而是「侧栏让位后没有任何 ≥768 的二次安全偏移」）。

### 2.3 为什么 880（≥768）完全没吃到 3B 的顶栏避让
- 3B 全部顶栏避让在 `mobile-adapt.css` **§20**，两条 `@media` 都写死 `max-width: 767.98px`：
  - `main[data-slot="sidebar-inset"]{ padding-top:44px }`（:651-656）/ 触屏 56（:657-661）
  - `[data-slot="panel-shell-header"]{ padding-block-start:0; padding-inline:16px !important }`（:664-669）
  - **880 > 767.98 → 以上一条都不命中**，880 是「未覆盖带」。
- 同时 §20 又把顶栏改成**所有宽度**不透明实底：`.window-chrome{ background:var(--mtx-bg)!important; box-shadow:… }`（:644-647，媒体查询外，全宽生效）。→ 任何落在 y∈[0,40) 的标题都被这层实底盖住，只剩 logo「M·O」(z-60, 12–84) 可见 → 观感即「标题与 M·O 重叠/被压」。
- 官方在 ≥768 靠 `compact-header:ps-[var(--window-chrome-safe-area-leading)]`（=160px，`globals.css:727-730` 定义于 `.web-window-chrome`）做横向让位；但该分支在本机 3B 实测**没有把标题推离左缘**（实测收起后标题仍在 x≈8，而非 8+160=168）。即：**≥768 折叠态下「官方向右让位」与「3B 纵向让位」双双缺位** → 落到 M·O 热区。

### 2.4 docs/10 §6.2 现成配方能否直接套？
- **选择器可 100% 复用**：§6.2 用的就是 `main[data-slot="sidebar-inset"]`（竖移）+ `[data-slot="panel-shell-header"]`（归零/横移），与本页 DOM 完全对应。
- **但断点门槛不能照抄**：§6.2（= 现 `mobile-adapt.css` §20）只作用于 `<768`；K60 在 880。所以**不能直接套**，必须把作用域从「`max-width:767.98px`」扩到「`≥768` 且 `data-state=collapsed`」。另外因为顶栏已改**实底**，640–767 原来的「同行 ps-160」同行方案也会被实底盖住（见 `renderer-overrides/fix17-复核-顶栏遮挡回归.md` 已结论），故 3B 统一走**竖向下移**，同行横移仅作兜底。

### 2.5 可直接落的 CSS（补 ≥768 折叠态，竖移为主，与 <768 同款）
```css
/* D-3B-03 修复：把 §20 的竖移配方扩展到「≥768 且侧栏折叠」，
   与 <768 配方完全同构，避免实底顶栏压字 / M·O 重叠 */
@media (min-width: 768px) {
  html.mtx-mobile .group\/sidebar-wrapper[data-state="collapsed"] main[data-slot="sidebar-inset"] {
    padding-top: 44px !important;
    box-sizing: border-box;
  }
  html.mtx-mobile .group\/sidebar-wrapper[data-state="collapsed"] [data-slot="panel-shell-header"] {
    padding-block-start: 0 !important;
    padding-inline: 16px !important;
  }
}
@media (min-width: 768px) and (pointer: coarse) {
  html.mtx-mobile .group\/sidebar-wrapper[data-state="collapsed"] main[data-slot="sidebar-inset"] {
    padding-top: 56px !important;
  }
}
```
> 备选（若产品坚持同排横移而非竖移）：`…[data-state=collapsed] [data-slot=panel-shell-header]{ padding-inline-start: calc(160px + var(--mtx-safe-left)) !important }`；但因顶栏实底，需同时保证标题纵向仍在 40px 带外，否则仍被压。**首选上表竖移方案**（与既有 <768 一致，无双倍风险、不改 z-index、不用 `:has`）。

## 3. D-3B-04：侧栏隐藏后「切换边栏」难召回

### 3.1 召回入口与层级核验
- 按钮：`[data-slot="sidebar-trigger"]`（`sidebar.tsx:278-306`，`variant=ghost size=icon class="size-7 …"` = **28×28**）。
- 它位于顶栏子槽 `window-chrome.tsx:270` 的 `div.app-no-drag.relative.z-[60]` 内 → **z-60，高于内容标题 z-40**。故「点不动」**不是**被下载筛选栏（z-40）或 overlay 拦截；内容层 z 低于顶栏控件。
- 实测折叠后内容左边界 x=8，与按钮热区（94–134）横向不重叠，故也不是「被标题覆盖吃点击」。真正问题是：**28px 触控热区太小**（低于 44dp 规范），加上折叠后左侧内容整体左移、观感拥挤，用户难定位/命中。

### 3.2 可直接落的 CSS（扩热区到 ≥44dp，纯 CSS，无需改 JS）
既有提案 `renderer-overrides/proposal-3b-navfix.css` §1 已给成品，核心：
```css
.web-window-chrome [data-slot="sidebar-trigger"] {
  position: relative;
  z-index: 60;                 /* 与顶栏 leading 槽一致，盖过内容/顶栏本体 */
  pointer-events: auto;
}
.web-window-chrome [data-slot="sidebar-trigger"]::after {
  content: "";
  position: absolute;
  inset: -8px;                 /* 28 → 44 各向外扩 8px */
  min-width: 44px;
  min-height: 44px;
  pointer-events: auto;
}
```
（如需更强观感：折叠态给按钮加实底/描边，图标满不透明；详见同目录 `proposal-3b-navfix.md` §1 与 z-index 总表 §5。）

## 4. D-3B-02：仪表板底部「被切掉」

### 4.1 仪表板布局链（源码）
- 页：`dashboard-page.tsx:179-192` —— `<PanelShell … contentClassName="ps-2.5 pe-2 pt-4 pb-12"><DashboardGrid/></PanelShell>`（**无 footer**；`pb-12`=48px 是唯一底部预留，但在内容 flex 内）。
- 网格根：`dashboard-grid.tsx:1517` `div.@container.flex.min-h-0.flex-1.flex-col`。
- 滚动容器：`dashboard-grid.tsx:1534` `div.flex.min-h-0.flex-1.flex-col.overflow-y-auto.@[560px]:overflow-visible`。
- 网格本体：`dashboard-grid.tsx:1539-1544` `relative grid grid-cols-1 gap-4 … @[560px]:flex-1 @[560px]:grid-cols-4 @[560px]:grid-rows-[repeat(3,minmax(8rem,1fr))] @[560px]:auto-rows-[minmax(8rem,1fr)]`；代码注释（:1530-1533）明说：**≥560px「grid is height-clamped again … no scrolling」**。

### 4.2 机制①（主因）：≥560px 高度钳制 + 无滚动 → 被 overflow-hidden 祖先裁切
- K60 880 展开：内容宽 ≈880−200−16 ≈ 664 ≥560；收起 ≈864 ≥560。两态都进「3 行 1fr、`overflow-visible`、不滚动」分支。
- 每行 `minmax(8rem,1fr)`：**下限 128px**，3 行 + 2×16 间距 ≈ **416px** 起。视口可用高度（扣顶栏 40 + header ~80 + 安全区）< 416 时，行不能缩到 128 以下，网格又 `overflow-visible` 且内层不滚 → 底部整行溢出网格盒。
- 溢出的落点被上层 `overflow-hidden` 裁掉：`app-layout.tsx:141` 出口容器 `div.min-h-0.flex-1.overflow-hidden` 与 `SidebarInset` 的 `overflow-hidden`（`app-layout.tsx:122`）。→ 视觉「底部被切片」。
- 为何 K60 880 竖屏看着正常：竖屏高度足够容纳 3×128+间距，1fr 还能拉伸填满；**一旦高度不够（横屏 / 分屏 / 放大卡片 / 更小屏）就现形**。`pb-12`(48) 在钳制盒内部，救不了被裁的行。

### 4.3 机制②（叠加）：底部悬浮条 `#mtx-float-nav` 未计入底部预留
- `mobile-adapt.js:330-343` 注入 `#mtx-float-nav`：`position:fixed; left:50%; translateX(-50%); bottom:calc(8px + safe-bottom); z-index:99999`（「‹返回 / ⌂首页」药丸）→ 常驻底部中央、盖住一切。
- `mobile-adapt.js:228-233` 只为 `[data-mtx-bottom-bar], .mtx-bottom-bar` 量高写 `--mtx-bottom-bar`；**`#mtx-float-nav` 不是该类** → `--mtx-bottom-bar` 恒 0。
- 于是 `mobile-adapt.css:147-152` `main{padding-bottom: calc(var(--mtx-safe-bottom) + var(--mtx-bottom-bar))}` 只为手势条留白，**不为浮条留白** → 仪表板/列表最后一行落在浮条下方被压住。

### 4.4 可直接落的 CSS（两条，分别治两因）
```css
/* D-3B-02 ①：3B 手机下取消「≥560 高度钳制无滚动」，
   让网格按内容自动行高，并由父容器滚动，避免底部被 overflow-hidden 裁掉 */
html.mtx-mobile [data-testid="dashboard-grid"] {
  grid-template-rows: none !important;
  grid-auto-rows: minmax(8rem, auto) !important;
  min-height: 0 !important;
}
/* 让网格的直接滚动父（dashboard-grid.tsx:1534 那个 div）真正可滚 */
html.mtx-mobile div:has(> [data-testid="dashboard-grid"]) {
  overflow-y: auto !important;
  -webkit-overflow-scrolling: touch !important;
}

/* D-3B-02 ②：为底部悬浮条（#mtx-float-nav，约 40px 高 + 8px 边距）预留底部空间 */
html.mtx-mobile .mtx-scroll,
html.mtx-mobile [data-mtx-scroll],
html.mtx-mobile main {
  padding-bottom: calc(var(--mtx-safe-bottom) + 56px) !important;  /* 覆盖仅 safe 的旧值 */
}
```
> 或更彻底：让 `mobile-adapt.js` 把 `#mtx-float-nav` 也纳入 `--mtx-bottom-bar` 量测（`bar` 选择器加 `,#mtx-float-nav`），一劳永逸让所有 `calc(safe+bar)` 生效。

## 6. 未验证项 / 待真机确认
- **y 轴实测细节**：lead 报的 `y=7/8` 与源码推导「展开 y≈40、`<768` 竖移后 y≈44+」在纯 CSS 层存在出入，可能受 K60 WebView 的 `devicePixelRatio / viewport-fit / 实底条含 safe-top` 影响。**结论不依赖 y 精确值**：横向 `200→8` 已由 `SidebarInset ms-2` 精确坐实；纵向上因顶栏已实底，3B 必须竖移（不能靠同行横移）——此结论成立。
- **`--window-chrome-safe-area-leading` 在 3B 是否解析为 160**：实测收起后标题未右移，说明该横向兜底在本机未生效（或 compact-header 分支在该构建未命中）。建议真机 DevTools 读该元素 computed `padding-inline-start` 与 `--window-chrome-safe-area-leading` 值坐实；无论结果如何，「≥768 折叠态缺统一竖移」都是必修项。
- **D-3B-02 是否在 880 竖屏现形**：按源码判断需「可用高度 < ≈416px」才裁；lead 880 竖屏看到活动卡完整 → 与判断一致（高度够）。请在**横屏 / 分屏 / 放大卡片**下复测底部行是否被切，以验证机制①。
